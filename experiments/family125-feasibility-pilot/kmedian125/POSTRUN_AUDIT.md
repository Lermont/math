# Уточнение сертификата после завершения запусков

380/380 запусков `pilot-20261011-v1` завершены 11.10.2026 22:22:09 MSK.
При проверке обнаружено, что запланированный корректный сертификат
`sum(alpha)-k*max(facility_charge)` бывает слабее самого LP: в нём не используется
ограничение y_i<=1. Решения, seeds, алгоритмы, бюджеты, сырые результаты и время
не изменяются. Первоначальные таблицы сохранены как `summary-planned-bound.csv`,
`summary-planned-bound.json` и `TABLES-planned-bound.md` внутри run-каталога.

В дополнение для всех экземпляров без исключения проверяется более сильный
сертификат на тех же сохранённых ценах alpha. Это статическая проверка нижней
границы; оптимизационные методы повторно не запускались.

Для каждой цены alpha_j определим b_i=sum_j max(alpha_j-d_ji,0). Для любого
множества S из k различных кандидатов:

```
sum_j d(j,S) >= sum_j alpha_j - sum_{i in S} b_i
             >= sum_j alpha_j - sum(k largest b_i).
```

Первое неравенство следует поклиентно из
`max(0,alpha_j-min_{i in S} d_ji) <= sum_{i in S} max(0,alpha_j-d_ji)`.
Эквивалентная LP-двойственная запись использует lambda, равную k-й по величине
b_i, и gamma_i=max(b_i-lambda,0) для y_i<=1. Все alpha хранятся как целые
числители на знаменателе 10^6; вычисления проверки — Python integers.
Целая целевая функция позволяет взять ceil(LB). Совпадение с допустимой
стоимостью является доказательством оптимальности, не доверием к округлённому
значению численного LP.

`certify.py` и отдельные тесты добавлены после бенчмарка. Их работа не скрыта во
времени эвристик: `verification.json` и `bounds.json` хранят время post-run audit
и сам сертификат. Запланированные 84 исходных сертификата также проверены.
Итоговые таблицы используют усиленную общую границу для всех методов; результаты
с первоначальной границей доступны для сравнения. Это уточнение качества
свидетельства, не изменение измеренных алгоритмов или подбор к успешному seed.
